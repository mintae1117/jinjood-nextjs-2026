- **Production**: https://jinjood.com

### 1. 사업자 등록 / 인허가 (법적 필수 - 최우선)

#### 1-1. 통신판매업 신고

- **현재 상태**: 사업자등록번호(452-23-00331)는 있으나, **통신판매업 신고** 여부 확인 필요
- **필수 조건**: 온라인으로 상품을 판매하려면 관할 구청(수영구청)에 통신판매업 신고 필수
- **준비물**:
  - 사업자등록증 사본
  - 구매안전서비스 이용확인증 (PG사 계약 후 발급)
  - 도메인 등록 확인
- **미신고 시**: 과태료 최대 1,000만원, 영업정지 가능
- **소요 시간**: 신청 후 약 3~7일

#### 1-2. 식품 관련 인허가 확인

- 이미 오프라인 매장을 운영 중이므로 **식품제조가공업** 또는 **즉석판매제조가공업** 허가가 있을 것
- 온라인 판매 시 별도 추가 허가가 필요한지 관할 보건소에 확인
- **식품 표시 기준**: 온라인 판매 시 아래 항목을 상품 페이지에 표시 의무
  - 원재료명
  - 알레르기 유발물질
  - 유통기한
  - 보관방법

#### 1-3. 구매안전서비스 가입 (에스크로)

- 전자상거래법상 **연매출 기준에 따라** 에스크로 또는 소비자피해보상보험 가입 필수
- PG사(토스페이먼츠 등) 계약 시 자동으로 충족되는 경우가 많음

### 2. PG사(결제대행사) 선정 및 계약

#### 2-1. PG사 선정: 토스페이먼츠 ⭐

KG이니시스·나이스페이·포트원과 비교 검토한 결과 **토스페이먼츠 선정** — Next.js용 React SDK(`@tosspayments/tosspayments-sdk`) 공식 제공, 한국어 문서 우수, **가입비/연회비 0원**, 카카오페이/네이버페이/토스페이를 추가 계약 없이 결제창에서 함께 지원, 정산 D+2 영업일. 진주떡집 규모(단일 매장·식품)에는 통합 솔루션(포트원)보다 단일 PG 직접 연동이 단순하고 비용 효율적.

#### 2-1-1. 결제수단별 수수료 (토스페이먼츠 기준 · 예시 범위)

PG 수수료는 "카드 한 종류"가 아니라 **결제수단마다 다릅니다.** 떡집 매출 구성에 따라 실효 수수료가 달라지므로 아래를 함께 검토하세요.

| 결제수단 | 예상 수수료 | 비고 |
|---------|-----------|------|
| **신용/체크카드** | 약 2.0~3.3% | 영세·중소 가맹점 우대수수료 적용 시 더 낮아질 수 있음 |
| **계좌이체** | 약 1.0~1.8% | 카드보다 저렴 |
| **가상계좌(무통장입금)** | 건당 약 300~500원(정액) | 비율이 아닌 **건당 고정 수수료** → 고액 주문(이바지·답례떡)에 유리 |
| **휴대폰 소액결제** | 약 3.5~5.5% | 수수료 높음 → 식품에는 비권장 |
| **카카오페이/네이버페이** | 약 2.0~3.5% | 간편결제사 수수료가 PG 수수료에 포함/별도일 수 있음 |

> **포인트**: 고객 단가가 높은 **이바지떡·답례떡·선물세트**는 가상계좌(정액 수수료)를, 단가 낮은 일반 떡은 카드/간편결제를 유도하면 전체 수수료를 줄일 수 있습니다.

#### 2-1-2. 영세·중소 가맹점 우대수수료

- 연매출 구간에 따라 카드 **우대수수료율**(영세일수록 낮음) 적용 — 계약 시 오프라인 매출 자료로 우대 적용 여부를 반드시 문의. 신규는 일반 요율 시작 → 매출 확정 후 재산정이 일반적.
- 간편결제는 토스 계약만으로 함께 노출됨. 네이버페이 "주문형"은 별도 입점 심사 필요 → PG 통합 "결제형"부터 시작.

#### 2-2. PG사 계약 시 준비 서류

- 사업자등록증 사본
- 통신판매업 신고증
- 대표자 신분증
- 사이트 URL (실제 동작하는 상태여야 함)
- 판매 상품 설명 (식품 카테고리)
- 정산 계좌 정보 (부산은행 112-2038-7604-08 / 정은아)

#### 2-3. 심사 및 소요 기간

- PG사 심사: 보통 **3~7 영업일**
- 식품 판매의 경우 추가 서류 요청 가능 (식품 인허가 관련)

### 2.5. 예상 비용 산정

#### 2.5-1. 초기(일회성) 비용

자체 개발 기준 **약 5~6만원 수준** — 통신판매업 등록면허세(약 40,500원/년) + 도메인(약 1.5~2만원/년, 이미 보유). PG 가입비/셋업비는 토스 기준 0원.

#### 2.5-2. 변동 비용 — 결제 수수료 (가장 중요)

- 매출에 비례하는 핵심 비용. 실효 요율 2.8% 가정 시 월 매출 100만원 → 수수료 약 2.8만원, 500만원 → 약 14만원, 1,000만원 → 약 28만원.
- 고단가 주문에 **가상계좌(건당 정액 ~500원)** 비중을 높이면 실효 요율을 2%대 초반까지 낮출 수 있음 (예: 5만원 주문 → 카드 1,400원 vs 가상계좌 500원).

#### 2.5-3. 매월 고정 인프라 비용 (현재 스택 기준)

| 항목 | 무료 구간 | 유료 전환 시 | 비고 |
|------|----------|-------------|------|
| **호스팅/배포** — Netlify로 이전 결정(§10 Phase B-0) | Free **$0** (상업 사용 허용) | 월 한도 초과 시 유료 전환(즉시 재개) | Vercel 잔류 시엔 Pro $20/월 필요(Hobby는 상업 사용 금지 약관) |
| **Supabase** (DB/Auth/Storage) | Free **$0** (500MB DB, 1GB Storage, **egress 월 ~5GB**) | Pro **$25/월(약 3.5만원)** | ⚠️ 이미지를 Storage에서 직접 서빙하면 egress 5GB 초과 위험 → **Netlify Image CDN 경유로 전환**(§10 Phase B-0 6번)하면 무료 유지. DB 용량·트래픽 증가 시에만 Pro |
| **도메인** | — | 약 1.5~2만원/년 | 연 단위 |
| **이메일 발송**(주문 확인 메일, 선택) | 무료 구간 有 | 사용량 기반 | Resend 등 외부 서비스 도입 시 |
| **고정비 합계** | **$0 (Netlify+Supabase 무료)** | 최대 약 3.5만원/월 (Supabase Pro 전환 시) | 결제 오픈 후에도 고정비 0원으로 시작 가능 |

> ✅ **호스팅은 결제 개발 착수 전 Netlify 무료로 이전 결정** (§10 Phase B-0) — 상업 사용 명시 허용이라 **결제 오픈 후에도 호스팅 고정비 0원**. Vercel Hobby는 상업 사용 금지 약관 때문에 제외. Netlify 월 한도(함수 12.5만 호출·대역폭 100GB) 초과 시 당월 정지되므로 사용량 모니터링 필수 (§5.5-15). **Supabase Pro는 무료 + pg_dump 자동 백업으로 시작하고 월 매출 ~300만원 안정화 시 전환** (§5.5-15).

#### 2.5-4. 종합

비용의 대부분은 **매출 비례 결제 수수료(약 2~3%, 영세 가맹점 우대수수료 적용 시 1%대)**. 인프라 고정비는 Netlify+Supabase 무료로 **0원 시작**, 매출 안정화 후 최대 월 3.5만원(Supabase Pro). 자체 개발 시 초기 비용은 사실상 통신판매업 신고비 수준.

### 3. 법적 문서 업데이트

#### 3-1. 이용약관 업데이트 필요 사항

현재 `src/components/legal/TermsContent.tsx`에 결제 관련 조항(제8~11조)이 이미 존재하지만, 실제 결제 도입 시 구체화 필요:

- **제9조 (결제방법)**: 실제 사용할 PG사와 결제 수단 명시
- **제10조 (배송)**: 배송비 정책 구체화 (현재 3,000원 고정이면 명시)
- **제11조 (환불/교환)**: 환불 처리 절차와 소요 기간 구체화
- **추가 필요**: 주문 취소 가능 시점 (결제 후 ~ 배송 전), 부분 환불 정책

#### 3-2. 개인정보처리방침 업데이트 필요 사항

현재 `src/components/legal/PrivacyContent.tsx`에 기본 구조는 있으나:

- **수집 항목 추가**: 배송지 주소, 수령인 이름, 수령인 연락처
- **위탁업체 구체화**: 실제 계약한 PG사명, 배송업체명 기재 필수
  - 예: "토스페이먼츠 주식회사 - 결제 처리"
  - 예: "CJ대한통운 - 배송 업무"
- **보유기간**: 전자상거래법에 따라 결제 기록 5년, 배송 기록 5년 보관 의무 명시

#### 3-3. 결제 시 필수 고지 사항 (전자상거래법)

결제 페이지에 반드시 표시해야 할 내용:

- 상품명, 수량, 가격
- 배송비
- 총 결제 금액
- 결제 수단
- **"구매 조건 확인 및 결제에 동의합니다" 체크박스** (필수)
- 환불/교환 불가 사유 고지 (식품 특성)
- 주문자 정보와 수령인 정보

**추가 표기 의무**: 통신판매업 신고 완료 후 **사이트 하단(footer)에 통신판매업 신고번호 상시 표기** 필요 (전자상거래법) — `src/data/sampleData`의 사업자 정보에 추가

#### 4-2. RLS 정책

- 사용자는 본인의 주문만 조회 가능
- 주문 생성은 인증된 사용자만
- 주문 상태 변경은 서버 측(service role)에서만

#### 4-3. 중요: 상품 스냅샷

- `order_items`에 주문 시점의 **상품명과 가격을 복사 저장**
- 나중에 상품 가격이 변경되더라도 주문 기록은 유지되어야 함
- ⚠️ 현재 `CartItem` 타입에는 가격 필드가 없고 조인된 `product.price`에서만 가격이 나옴 → 주문 생성 시 **클라이언트 장바구니 데이터가 아니라 서버에서 DB를 다시 조회**해 스냅샷 생성 (§5.5-6)

#### 4-4. 주문번호 생성 주의 (레이스 컨디션)

- `JJ-20260305-0001` 같은 일자별 일련번호를 앱 코드에서 `count + 1`로 만들면 **동시 주문 시 중복 발생**
- 대응: PK는 UUID를 그대로 쓰고, 표시용 주문번호는 **DB에서 생성** (PostgreSQL 시퀀스 또는 `order_number` UNIQUE 제약 + 충돌 시 재시도)

#### 4-5. 가상계좌 부가 정보

- 가상계좌 결제 시 은행명·계좌번호·입금기한을 고객에게 계속 보여줘야 함 → `payments`에 `vbank_bank`, `vbank_account`, `vbank_due` 컬럼 추가 (또는 초기엔 `raw_response`에서 파싱)
- 가상계좌 건 **환불 시 고객 환불계좌 수집 필요** (카드처럼 자동 환불 안 됨, §5.5-4)

#### 4-6. NULL 허용 설계

- `fulfillment_method = 'pickup'`이면 배송지 컬럼(postal_code, address 등)은 NULL 허용
- `desired_date`는 픽업/배송 모두 필수

### 5. 결제 플로우 설계

```
[장바구니] → [주문서 작성] → [결제 요청] → [PG사 결제창] → [결제 완료] → [주문 확인]
                                    ↓                              ↓
                               [결제 실패]                    [결제 승인 API]
                                    ↓                         (서버 검증)
                               [에러 안내]                         ↓
                                                          [주문 상태 업데이트]
                                                                  ↓
                                                          [장바구니 비우기]
```

#### 5-1. 상세 단계

**Step 1: 주문서 작성 페이지** (`/checkout`)

- 장바구니에서 넘어온 상품 목록 표시
- 배송지 입력 (우편번호 검색 API - 다음 주소 검색)
- 수령인 정보 입력
- 배송 메모 선택/입력
- 결제 수단 선택
- 최종 금액 확인
- 약관 동의 체크박스

**Step 2: 결제 요청** (클라이언트)

- 주문 정보를 서버에 보내서 `orders` 레코드 생성 (status: pending)
- PG사 SDK로 결제창 호출

**Step 3: 결제 승인** (서버 - Next.js API Route 또는 Server Action)

- PG사로부터 받은 `paymentKey`, `orderId`, `amount`를 서버에서 검증
- 토스페이먼츠 승인 API 호출 (`POST /v1/payments/confirm`)
- **금액 위변조 검증 필수**: DB에 저장된 주문 금액과 PG사 응답 금액을 서버에서 비교
- 성공 시: `orders.status = 'paid'`, `payments` 레코드 생성
- 실패 시: `orders.status = 'failed'`, 에러 로깅

**Step 4: 결제 완료 페이지** (`/checkout/success`)

- 주문번호, 결제 금액, 배송 예정 안내
- 주문 내역 페이지 링크

**Step 5: 결제 실패 페이지** (`/checkout/fail`)

- 실패 사유 안내
- 재시도 또는 장바구니로 돌아가기

#### 5-2. SDK 선택 (2026 기준)

- `@tosspayments/tosspayments-sdk` **v2 결제위젯(widgets)** 방식 권장 — 결제수단 UI·약관 동의 UI를 위젯이 제공해 직접 구현 범위가 줄어듦
- 이 프로젝트는 Next.js 16 (App Router) + React 19 → SDK 로드는 클라이언트 컴포넌트(`"use client"`)에서, 승인은 서버 Route Handler에서 분리
- 연동 시작 전 토스 **테스트 키**로 전 플로우 개발 가능 → PG 심사(§2-3)와 개발을 병렬 진행
- 토스 `orderId`는 자체 발급 문자열(6~64자) 필요 → `orders.id`(UUID)를 그대로 사용하면 매핑 테이블 불필요

#### 5-3. "바로 구매하기" 플로우 정의 (누락 주의)

- `ProductDetail`의 "바로 구매하기"는 **장바구니를 거치지 않는 플로우** → checkout을 장바구니 전용으로만 만들면 이 버튼은 연결할 곳이 없음
- 권장: 주문 생성 입력을 "구매 항목 배열"로 일반화하고, 바로 구매는 해당 상품 1건으로 checkout 진입 (장바구니를 오염시키지 않도록 sessionStorage/쿼리로 전달)
- 초기 단순화 옵션: 바로 구매 = "장바구니 담기 + `/checkout` 이동"으로 구현해도 무방 (단, 기존 장바구니 상품이 함께 주문됨을 고객에게 인지시킬 것)

### 5.5 실서비스에서 실제로 겪게 될 문제 & 대응 설계 (운영 리스크)

> "성공 케이스" 연동만 구현하면 실서비스에서 반드시 사고가 납니다. 실제 고객 대상 주문·결제 서비스를 운영하며 겪게 되는 문제와 이 프로젝트에서의 대응입니다. **§10 로드맵에 모두 반영되어 있습니다.**

#### 5.5-1. 주문이 들어와도 아무도 모르는 문제 (가장 치명적)

- 결제가 성공해도 사장님이 사이트를 계속 보고 있지 않으면 주문을 놓침. 떡은 신선식품 + 주문제작이라 **주문 누락 = 약속한 날짜에 떡이 없음 = 최악의 컴플레인**
- **대응 (오픈 전 필수)**:
  - 결제 완료 시 사장님에게 즉시 알림 — 초기: 이메일(Resend 무료 구간) 또는 SMS/카카오 알림톡(Solapi 등, 건당 10~20원)
  - 알림톡은 **카카오 비즈니스 채널 개설 → 발신프로필 등록 → 템플릿 사전 심사**(합쳐서 수일~2주) 필요 → Phase A에서 미리 진행
  - **최소 관리자 화면(주문 목록 + 상태 변경 버튼)을 Phase 5에서 결제 오픈 시점(Phase D)으로 앞당김** — 이것 없이는 사장님이 주문을 확인·처리할 방법 자체가 없음

#### 5.5-2. 돈은 빠졌는데 주문이 안 잡히는 문제 (결제-주문 정합성)

- 토스 승인 API는 성공했는데 직후 서버 오류/DB 쓰기 실패 → PG에는 결제 완료, DB에는 `pending`. 고객: "결제했는데 주문내역이 없어요"
- **대응**:
  - 승인 API route를 **멱등(idempotent)** 하게: 같은 `paymentKey`로 재요청 시 이미 처리됐으면 저장된 결과를 그대로 재반환 (새로고침·중복 클릭 대비)
  - `payments.raw_response`에 PG 원본 응답 반드시 저장 (분쟁·수동 복구 근거)
  - **일일 대사(reconciliation) 배치**: `pending`인데 30분 이상 지난 주문을 토스 결제 조회 API로 대조 → 실결제면 `paid` 복구, 미결제면 자동 취소. **Netlify Scheduled Functions**로 구현 (§10 Phase B-0 이전 결정 반영)

#### 5.5-3. 웹훅과 redirect의 레이스 컨디션

- 웹훅(입금 통지 등)이 success redirect보다 **먼저/늦게/중복** 도착할 수 있음 — 순서를 가정하면 안 됨
- **대응**:
  - 웹훅 핸들러도 멱등하게 (같은 이벤트 2번 처리해도 결과 동일)
  - 토스 웹훅은 **페이로드를 신뢰하지 말고 `paymentKey`로 결제 조회 API를 재호출해 확인 후 상태 변경** (토스 공식 권장 방식)
  - 상태 전이 규칙을 서버에서 강제: `paid → preparing → shipped → delivered` 순방향만 허용, `cancelled` 이후 변경 금지

#### 5.5-4. 가상계좌 특유의 상태 관리

- 가상계좌 **발급 ≠ 결제 완료**: 입금 전 `waiting_for_deposit` 상태 필요 (주문내역에 "입금 대기 - ○○은행 xxx-xxx 기한 ○월○일" 표시)
- 입금 기한 만료 시 자동 취소 처리 (웹훅 or 대사 배치에서)
- 환불 시 **고객 환불계좌 정보를 받아야 함** — 카드와 달리 자동 환불 불가. 취소 UI에 환불계좌 입력 단계 필요
- 고액 주문(이바지·답례떡)에 가상계좌 비중이 높을 것이므로 (§2-1-1) 이 플로우는 부가 기능이 아니라 핵심

#### 5.5-5. 떡집 특성: 주문제작 + 신선식품

- 떡은 재고 판매가 아니라 **주문 제작** → **희망 수령일 없이는 주문을 받을 수 없음** (기존 설계에 누락되어 있던 부분, §4-1에 반영)
  - `fulfillment_method`: 픽업(매장 수령) / 배송 — 남천동 인근 고객은 픽업 수요가 큼
  - `desired_date`: 최소 리드타임 정책 필요 (예: 주문일 +1일, 명절 시즌 +3일)
- **일일 생산 한도**: 명절 대목에 특정일 주문 폭주 시 그 날짜를 마감 처리할 수단 필요 → `site_settings`에 휴무일·주문마감일 관리 (초기엔 수동 등록으로 충분)
- **타임존 함정**: Vercel 서버와 DB는 UTC. "오전 10시 주문 마감", "내일 수령 가능" 판정은 반드시 `Asia/Seoul` 기준으로 계산할 것 (자정 전후 9시간 오차로 날짜가 밀리는 버그가 흔함)

#### 5.5-6. 가격/상품 검증 — 장바구니를 신뢰하지 않기

- 장바구니에 담은 뒤 상품 가격 변경·판매 중지(`is_active=false`) 가능 → **주문 생성 시 서버에서 DB 가격으로 전액 재계산**, 클라이언트가 보낸 금액은 대조용
- 판매 중지된 상품이 장바구니에 있으면 주문서에서 명확히 안내하고 제외
- 배송비 3,000원이 현재 `CartSummary.tsx`에 하드코딩 → `site_settings` 또는 서버 상수로 단일화 (클라이언트 표시값과 서버 계산값 불일치 방지)

#### 5.5-7. 취소/환불 운영

- 식품은 **단순변심 청약철회 제한 가능**(전자상거래법 제17조 2항)하지만, **결제 전에 고지해야만 유효** → 결제 페이지 + 약관에 명시 (§3-3)
- 취소 가능 시점 정책: **"제조 시작 전(= `preparing` 전환 전)까지 고객 직접 취소 가능, 이후 전화 협의"** 권장 — 주문제작 식품의 현실적 기준
- 토스 취소 API(`POST /v1/payments/{paymentKey}/cancel`)는 부분취소 지원하나 **초기엔 전체취소만 구현**해 단순화
- 취소 요청도 멱등 처리 (중복 클릭 = 중복 취소 API 호출 방지)

#### 5.5-8. 고객 커뮤니케이션

- 주문완료 / 입금확인 / 발송 시점에 **고객에게도 알림** (초기: 이메일, 추후: 알림톡)
- 주문내역 페이지에서 현재 상태를 한국어로 명확히: 입금대기 → 결제완료 → 제조중 → 발송(픽업준비완료) → 완료
- CS 유입 대비: 주문내역·완료 페이지에 매장 전화번호(051-621-5108) 상시 노출

#### 5.5-9. 모니터링 / 장애 대응

- 결제 승인 실패·웹훅 처리 실패를 `console.log`로만 남기면 아무도 모름 → 최소한 **실패 시 관리자 이메일 알림** + Vercel 로그 확인 체계, 여유 되면 Sentry 도입
- 토스 대시보드(결제내역)와 자사 DB를 오픈 초기 매일 눈으로 대조하는 운영 루틴 권장 (§5.5-2 배치가 있어도 초기엔 이중 확인)
- 매출·정산·결제내역 관리 화면은 자체 구현하지 말 것 — **토스 상점관리자 대시보드**가 이미 제공 (자사 관리자 화면은 주문 처리용 최소 기능만)

#### 5.5-10. 비회원 주문 (정책 결정 사항)

- 현재 장바구니·구매는 **로그인 필수** 전제 — 초기엔 회원 전용으로 시작해 복잡도를 낮추는 것 권장
- 단, 중·장년 고객층 특성상 회원가입이 이탈 요인이 될 수 있음 → 오픈 후 전환율을 보고 비회원 주문(주문번호+전화번호 조회) 도입 검토

#### 5.5-11. 택배 배송 운영 (운송장 · 배송조회 · 배송 사고)

- **운송장 흐름**: 관리자 화면에서 택배사 + 운송장 번호 입력 → `status = shipped` 전환 + 고객 발송 알림 + 마이페이지 주문 상세에 **배송조회 링크** 노출 (초기엔 택배사 조회 페이지 URL에 운송장 번호를 붙인 단순 링크로 충분, API 연동 불필요)
- **desired_date 선택 제한**: 택배는 일요일/공휴일 배송 없음 → 희망일 달력에서 주말·공휴일·택배사 휴무(명절 집하 마감)를 선택 불가 처리
- **제주/도서산간**: 다음 주소 API의 우편번호로 판정 → 추가 배송비 부과 또는 **초기엔 "제주/도서산간 배송 불가"로 단순화** (신선식품은 배송일 +1일이라 품질 리스크도 큼 — 정책 확정 필요 §11)
- **배송 사고(파손·신선도 저하)**: "수령 당일 사진과 함께 연락" 기준을 주문 완료 페이지·약관에 안내하고, 재발송/환불 판단 기준을 사전 정의 — 신선식품은 반품 회수가 무의미하므로 사진 확인 → 재발송이 현실적

#### 5.5-12. 회원 탈퇴와 주문 기록 보존 (법적 함정)

- 전자상거래법상 **결제·배송 기록 5년 보관 의무** → 탈퇴 시 orders/payments가 함께 지워지면 위법
- 기존 `cart_items`는 `user_id ... ON DELETE CASCADE` — **이 패턴을 orders에 복사하면 안 됨**. `orders.user_id`는 `ON DELETE SET NULL`
- 주문에 필요한 정보(수령인 등)는 orders에 스냅샷으로 남고, 탈퇴 회원 개인정보는 분리 보관 원칙 → 개인정보처리방침에 명시 (§3-2)

#### 5.5-13. 관리자 권한 체계 (현재 부재)

- 프로젝트에 admin 개념이 없음 → `/admin/orders`를 만들어도 접근 제어 수단이 없음
- 초기 권장: `user_profiles`에 `role` 컬럼 추가(기본 `customer`, 수동으로 `admin` 지정) 또는 환경변수 이메일 화이트리스트로 시작
- 주문 상태 변경·운송장 입력 API는 **반드시 서버에서 admin 검증 후 Service Role 클라이언트로 실행** (클라이언트 RLS 우회 경로를 만들지 말 것)

#### 5.5-14. 과세/면세 구분 (부가세 — 결제 파라미터에 직결)

- 토스 결제 요청 시 면세 상품은 `taxFreeAmount`를 지정해야 함 — 잘못 설정하면 **토스 매출 자료와 부가세 신고 금액이 불일치**
- 떡류의 과세/면세 여부와 사업자 과세 유형(일반/간이)을 **세무사·국세청에 확인 후** 결제 파라미터 확정 (§11 체크리스트에 추가)

#### 5.5-15. 인프라: 백업 · 환경 분리 · 웹훅 등록 · Cron 제한

- **Supabase 무료 플랜은 자동 백업 없음** → 주문·결제 데이터 유실 시 복구 불가. 대응 두 가지:
  - **저비용 시작(권장)**: 무료 플랜 유지 + **GitHub Actions로 매일 `pg_dump` 자동 백업**(무료) — 결제 기록은 토스 상점관리자에도 이중 존재하므로 초기 리스크 감내 가능
  - **전환 트리거**: 월 매출 ~300만원(수수료 8만원대) 안정화 시 Pro($25/월, 7일 자동 백업) 전환 — 매출 대비 1% 수준이 되는 시점
- **호스팅: Netlify 무료로 이전 결정** (§10 Phase B-0) — Vercel Hobby는 Fair Use 가이드라인이 **"방문자 결제 요청/처리"를 상업 사용의 명시적 예시로 지목**해 결제 오픈 = 약관 위반(사전 통보 없이 정지 가능)이 되는 반면, **Netlify 무료 플랜은 상업 사용을 명시 허용** → 호스팅 고정비 0원 유지
  - **이전 타이밍**: 결제 개발 착수 전 필수 선행 — 웹훅 URL·스케줄 함수·환경변수가 플랫폼 종속이므로, 처음부터 최종 플랫폼에서 개발·테스트해야 "오픈 직전 인프라 교체" 리스크가 없음
  - Netlify 트레이드오프: 콜드스타트 ~3초(Vercel 대비 느림), 월 한도 초과 시 당월 정지(아래 모니터링 항목 참고)
  - 검토했던 다른 대안(기록용): Vercel Pro $20/월(이전 공수 0이나 고정비 최대) / Cloudflare Workers Paid $5/월(한도 여유 최고, OpenNext 이전 공수 — 추후 Netlify 한도가 반복적으로 문제되면 이쪽으로) / Oracle 무료 VPS(서버 직접 운영 부담으로 제외)
- **환경 분리**: 스테이징(토스 테스트 키) / 프로덕션(라이브 키)을 호스팅(Netlify) 환경변수의 컨텍스트별 설정으로 분리 — 테스트 결제가 실 DB·실 알림에 섞이지 않게
- **웹훅 URL 등록**: 토스 개발자센터에 배포 도메인 기준으로 등록 필요 (테스트/라이브 각각) — 코드만 만들고 등록을 빠뜨리면 웹훅이 영원히 안 옴
- **스케줄 작업**: 대사 배치는 **Netlify Scheduled Functions**(무료 플랜 가능, 함수 호출 한도에 포함) — 시간에 민감한 처리(가상계좌 입금·만료)는 스케줄러가 아닌 **웹훅**으로 처리
- **Netlify 무료 한도 모니터링**: 함수 12.5만 호출·대역폭 100GB/월 초과 시 당월 정지 → 사용량 알림 설정 + 명절 대목 전 잔여량 확인, 소진 조짐이면 유료 전환으로 즉시 재개 가능. 월 주문 ~100건(방문 3천~1만) 규모 추산 시 SSR 호출 3~8만 건으로 한도 내 여유
- **Supabase egress(전송량) 주의**: 무료 플랜 월 ~5GB — 이미지를 Storage에서 직접 서빙하면 이 규모 방문자로도 초과 위험 → **Netlify Image CDN 경유로 전환**(Phase B-0 6번)해 이미지 트래픽을 Netlify 100GB 쪽으로 이동

### 7. 보안 체크리스트

- [ ] **결제 금액 서버 검증**: 클라이언트가 보낸 금액을 절대 신뢰하지 않고, **서버에서 DB 상품 가격으로 재계산**한 주문 금액과 PG사 응답 금액을 비교 (§5.5-6)
- [ ] **승인/취소 API 멱등성**: 같은 `paymentKey` 재요청·중복 클릭에도 이중 처리 없도록 (§5.5-2, §5.5-7)
- [ ] **PG사 Secret Key**: 환경변수로만 관리, 클라이언트에 절대 노출 금지 (`TOSS_SECRET_KEY` - `NEXT_PUBLIC_` 접두사 없이)
- [ ] **Supabase Service Role Key**: `SUPABASE_SERVICE_ROLE_KEY` 서버 전용 관리 — `src/lib/supabase/admin.ts`에서만 사용, 클라이언트 번들에 포함 금지
- [ ] **웹훅 검증**: 페이로드를 신뢰하지 말고 결제 조회 API 재호출로 확인 후 상태 변경 (§5.5-3, 토스 권장)
- [ ] **HTTPS 필수**: Vercel 배포 시 자동 적용
- [ ] **카드번호 비저장**: PG사 SDK가 처리하므로 직접 수집/저장 절대 금지 (PCI-DSS)
- [ ] **SQL Injection 방지**: Supabase 클라이언트 사용으로 기본 방어됨
- [ ] **주문 상태 변조 방지**: 클라이언트에서 직접 status 변경 불가하도록 RLS 설정 + 서버에서 상태 전이 순방향 강제 (§5.5-3)
- [ ] **Cron 엔드포인트 보호**: `app/api/cron/*`은 `CRON_SECRET` 헤더 검증으로 외부 호출 차단

### 10. 구현 우선순위 로드맵 (2026-07-11 개정)

> **핵심 변경점**: ① PG 심사 대기 중에도 **토스 테스트 키로 전체 개발 가능** → Phase A와 B~D를 병렬 진행. ② 사장님 주문 알림·최소 관리자 화면·대사 배치를 "선택"이 아닌 **오픈 필수(Phase D~E)** 로 승격 — 이것 없이 오픈하면 §5.5-1/2의 사고가 실제로 발생함. ③ 수령 방식(픽업/배송)·희망 수령일이 주문서와 DB에 포함됨. ④ **호스팅을 결제 개발 착수 전 Netlify 무료로 이전(Phase B-0)** — 상업 사용 허용으로 고정비 0원 (§5.5-15). Cron·웹훅·환경변수가 플랫폼 종속이므로 반드시 결제 개발보다 선행.

#### Phase A: 사전 준비 (개발과 병렬 진행 - 1~2주)

1. 통신판매업 신고 확인/진행 (대표)
2. PG사(토스페이먼츠) 가입 신청 및 심사 — **심사 대기 중 테스트 키 발급받아 Phase B~D 개발 병행**
3. **사업 정책 확정** (§11 체크리스트):
   - 배송비, 배송 가능 지역(**제주/도서산간 취급 여부** §5.5-11), 주문 마감 시간
   - **수령 방식**: 픽업만? 픽업+배송? / **희망 수령일 최소 리드타임** (예: +1일, 명절 +3일)
   - **취소 가능 시점** (권장: 제조 시작 전까지) / **배송 사고(파손·신선도) 보상 기준** (§5.5-11)
4. 택배사 선정 (배송 제공 시)
5. **알림 채널 결정** — 알림톡 사용 시 카카오 비즈니스 채널 개설 + 템플릿 심사(합쳐서 수일~2주)를 지금 진행 (§5.5-1)
6. **과세/면세 확인** — 떡류 부가세 구분·사업자 과세 유형을 세무사에 확인 (§5.5-14, 결제 파라미터 `taxFreeAmount`에 직결)

#### Phase B-0: 호스팅 이전 — Vercel → Netlify 무료 (결제 개발 착수 전 선행, 1~2일)

> Netlify 무료 플랜은 **상업 사용을 명시적으로 허용**(Vercel Hobby와의 결정적 차이) → 결제 오픈 후에도 호스팅 고정비 0원. 단 월 한도(함수 12.5만 호출·대역폭 100GB) 초과 시 당월 정지되므로 사용량 모니터링 필수 (§5.5-15).

1. Netlify 사이트 생성 + GitHub 저장소 연동 (Next.js 16 공식 런타임 자동 적용 확인, 빌드 성공 검증)
2. 환경변수 이전 (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`)
3. Netlify 서브도메인으로 전체 기능 검증: SSR 페이지·styled-components·이미지(Supabase Storage)·카카오맵·로그인(이메일/카카오/구글)·장바구니 — 도메인이 `jinjood.com` 그대로 유지되므로 Supabase Site URL·OAuth 설정은 변경 불필요
4. `jinjood.com` DNS를 Netlify로 전환 (전환 직후 재검증)
5. 결제 설계 치환 확정: 대사 배치는 Vercel Cron 대신 **Netlify Scheduled Functions**(§5.5-2), 토스 웹훅 URL은 Netlify 배포 도메인 기준
6. **이미지 서빙 경로 전환**: `next/image`의 `unoptimized` 제거 + `next.config`의 `remotePatterns`에 Supabase Storage 도메인 등록 → **Netlify Image CDN**이 이미지를 서빙 — 이미지 트래픽이 Supabase 무료 egress(월 ~5GB, 이 규모 방문자면 초과 위험)가 아닌 Netlify 대역폭(100GB)으로 계산되고 자동 리사이즈·캐싱까지 적용됨
7. Vercel 프로젝트 배포 중지 (중복 배포·혼선 방지 — 삭제 대신 비활성화로 롤백 여지 유지)
8. Netlify 사용량 알림 설정 (함수 호출·대역폭 — 명절 대목 한도 소진 조기 감지) + Supabase 대시보드에서 egress 사용량 확인 습관

#### Phase B: 기반 구축 (1주)

1. DB 테이블 생성: orders(+ fulfillment_method, desired_date, 운송장 컬럼, `user_id ON DELETE SET NULL` §5.5-12, waiting_for_deposit 상태), order_items(가격 + **options 스냅샷**), payments + RLS + 상태 전이 규칙 (§4)
2. 타입 정의 (`Order`, `OrderItem`, `Payment`, `OrderStatus` 등)
3. `src/lib/supabase/admin.ts` — Service Role 클라이언트 (서버 전용)
4. **관리자 권한 체계** — `user_profiles.role` 또는 이메일 화이트리스트 + admin RLS 정책 (§5.5-13)
5. 주문/결제 서비스 레이어 (`orders.ts`, `payments.ts`) — 주문 생성 시 서버 가격 재계산·스냅샷 (§5.5-6)
6. 배송비 등 정책 값을 `site_settings`/서버 상수로 단일화 (CartSummary 하드코딩 제거)
7. 이용약관/개인정보처리방침 업데이트 (§3, 식품 청약철회 제한 고지·배송 사고 기준·footer 통신판매업 번호 표기 포함)

#### Phase C: 결제 플로우 개발 (1~2주, 토스 테스트 키)

1. 주문서 작성 페이지 — 수령 방식(픽업/배송) 선택, **희망 수령일 선택(휴무일·주말/공휴일·마감일 반영 §5.5-11)**, 배송지 입력(다음 주소 검색, 제주/도서산간 우편번호 판정)
2. 토스페이먼츠 SDK v2 결제위젯 연동 (`@tosspayments/tosspayments-sdk`, 과세/면세 파라미터 반영 §5.5-14)
3. 결제 승인 API Route — 금액 서버 검증 + **멱등 처리** (§5.5-2)
4. 결제 성공/실패 페이지 (가상계좌면 입금 안내 표시)
5. 장바구니 → 주문 전환 + 결제 성공 시 `clearCart()`
6. **"바로 구매하기" 플로우 연결** (§5-3 — 장바구니를 거치지 않는 경로 정의)

#### Phase D: 주문 관리 + 운영 필수 기능 (1~2주)

1. 마이페이지 주문 내역 (`/mypage/orders` 빈 UI → `orderService` 연결) + 주문 상세 — **결제 영수증(`receipt_url`)·배송조회 링크·가상계좌 입금 안내 노출** (결제내역 조회는 이 페이지가 담당, 매출 관리는 토스 상점관리자 활용 §5.5-9)
2. 주문 취소 기능 (전체취소, 멱등, 가상계좌면 환불계좌 입력 §5.5-4/7)
3. **사장님 신규 주문 알림** (이메일 또는 알림톡) — 오픈 필수 (§5.5-1)
4. **최소 관리자 화면**: 주문 목록 + 상태 변경 + **택배사/운송장 번호 입력**(→ 발송 알림·고객 배송조회 §5.5-11) (`/admin/orders`, admin 권한 검증 §5.5-13) — 오픈 필수
5. 고객 알림 (주문완료/입금확인/발송 — 초기엔 이메일로 충분 §5.5-8)

#### Phase E: 안정화 & 오픈 (1주)

1. 웹훅 처리 (가상계좌 입금 통지·입금 기한 만료 — 멱등 + 재조회 검증 §5.5-3/4)
2. **대사 배치** (Vercel Cron — pending 방치 주문 복구/취소 §5.5-2)
3. 현금영수증 처리 (§8-1)
4. **테스트 키 전 시나리오 리허설**: 결제 중 이탈, 성공 페이지 새로고침, 승인 중복 클릭, 가상계좌 입금·만료, 취소, 판매중지 상품 주문 시도, 자정 전후 마감시간 판정(§5.5-5), 바로 구매 경로, 운송장 입력→배송조회
5. **오픈 준비 전환 작업** (§5.5-15): 토스 개발자센터 웹훅 URL 라이브 등록, Netlify 환경변수 라이브 키 설정(테스트/프로덕션 컨텍스트 분리), **Netlify 사용량 알림·잔여 한도 재확인**, DB 백업 체계 확보(무료: pg_dump 자동 백업 / 매출 안정화 후: Supabase Pro), footer 통신판매업 신고번호 표기
6. 라이브 키 전환 → 구매 버튼 활성화(ProductDetail/CartSummary 핸들러 교체) → **소프트 오픈** (지인 실결제 주문 1~2건으로 알림·운송장·정산까지 검증 후 공개)

### 11. 개발 전 반드시 확인할 사항 (체크리스트)

| 항목 | 담당 | 상태 |
|------|------|------|
| 통신판매업 신고 | 대표(정창구) | 확인 필요 |
| 식품 온라인 판매 인허가 | 대표 | 확인 필요 |
| PG사 계약 (토스페이먼츠 추천) | 대표 + 개발자 | 미진행 |
| 배송비 정책 확정 | 대표 | 3,000원 고정? |
| 배송 가능 지역 확정 | 대표 | 전국? 부산만? |
| **수령 방식 확정 (픽업/배송)** | 대표 | 픽업만? 둘 다? (§5.5-5) |
| **희망 수령일 최소 리드타임** | 대표 | 예: +1일, 명절 +3일 (§5.5-5) |
| **취소 가능 시점** | 대표 | 권장: 제조 시작 전 (§5.5-7) |
| **제주/도서산간 취급 여부** | 대표 | 추가 배송비 or 배송 불가 (§5.5-11) |
| **배송 사고 보상 기준** | 대표 | 파손·신선도 → 재발송/환불 기준 (§5.5-11) |
| **과세/면세 구분 (부가세)** | 대표 + 세무사 | `taxFreeAmount` 파라미터에 직결 (§5.5-14) |
| 주문 마감 시간 확정 | 대표 | 미정 |
| 택배사 선정 | 대표 | 미정 |
| **주문 알림 채널 (이메일/알림톡)** | 대표 + 개발자 | 알림톡이면 카카오 채널 개설+템플릿 심사 선행 (§5.5-1) |
| 이용약관 업데이트 | 개발자 | 결제 도입 시 필요 (청약철회 제한·배송 사고 기준 고지 포함) |
| 개인정보처리방침 업데이트 | 개발자 | PG사 확정 후 필요 (탈퇴 시 기록 분리 보관 §5.5-12 포함) |
| **footer 통신판매업 번호 표기** | 개발자 | 신고 완료 후 (§3-3) |

> 사업 정책(배송, 결제수단 등)이 확정되면 개발 착수가 가능합니다.
